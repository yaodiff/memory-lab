# 规范：一轮记忆系统迭代怎么走

[← 改哪块先读哪份](README.md)

来源：一个内部场景里约一周的迭代（检索腿取舍、类型过滤、孤立页清理、后台任务状态、领取公平、与外部手册重复的页），只留不依赖内部背景的通用做法。数字门槛是那一轮实际用的值，来自内部小样本，不是推导出的最优值。关联 [#40](https://github.com/yaodiff/memory-lab/issues/40)、[plan](../plans/team-memory-quality/README.md)、[记忆整理教训](memory-curation.md)与[记忆评测教训](memory-eval.md)。

每一步都写了「门槛」。没过门槛不进下一步。

```
bad case / 指标 ──► 1 登记假设 ──► 2 只读回放 + 单条件对照 ──► 定位：召回 / 内容 / 采纳
                                                          │
                     ┌────────────────────────────────────┴──────────────┐
                     ▼                                                   ▼
        3 内容侧：试点 → 独立复核 ≥90% → 分批放量        4 召回/代码：草稿 PR → 开发组对比 → 冻结组不退化
                     └────────────────────┬──────────────────────────────┘
                                          ▼
                    5 上线：批准 → 先后端后客户端说明 → 生产重跑 + 读回版本
                                          ▼
                    6 留痕：内部记录 / 公开实验 / 评测集开发组
```

## 1. 登记假设

- 入口是一条 bad case 原句，或一个指标异常。
- 登记一条可证伪的假设：原指标及版本、现象、数据在哪、怎么验证、能否用公开或合成数据复现。
- **事前写判定线**：什么读数算 Works，什么算 Does not work，其余是 Inconclusive。
- 门槛：判定线在看结果前写下，带时间。没有事前判定线的结论，复盘时要明说「判定线为事后整理」。

## 2. 只读回放与单条件对照

- 用 bad case **原句**和原请求参数，在生产环境做只读回放，不改写 query；原请求省略的参数也照样省略。回放请求带测试流量标记，免得污染线上指标。
- 每个回执保存原 query、实参、候选 ID、分数和可追踪的请求 ID。
- 把问题定位到一层：
  - **召回**：正确页在库里，但没进前 10，或被错页压住；
  - **内容**：正确页排进来了，但正文错、过时、缺入口或类型标错；
  - **采纳**：前 3 有正确页，Agent 没读原文或没照做。
- 做一组**去掉单个条件**的对照：每次只去掉一路召回、一个类型限制、一步重排或一页，其余不变，看正确页和错页的名次怎么动。
- 门槛：定位有回执支撑，单条件对照能复现差异。复现不了，就不改。

## 3. 内容侧改动：试点 → 独立复核 → 分批放量

- **先抽小批试点**，几十页量级。
- **独立复核判正确率**：复核者不能是产出判定的同一个模型、同一轮；对照代码和全文，不只看摘要或前几行。模型复核要写明是模型复核。
- 门槛：独立复核正确率 **≥90%** 才放量；不到就换判定方法重新试点。
- **每一批**：写前整页备份到持久位置 → 带版本号的条件写入 → 写后读回核对 → 跑这批相关的正例回放。正例退化或读回不一致，就**回滚这一批**并停止放量。

## 4. 召回或代码改动：草稿 PR → 开发组 → 冻结组

- 先开草稿 PR，本地构建和单测通过后再转为可评审。
- 在评测集**开发组**上和同时段的线上基线对比，至少报：前 1 / 3 / 10 命中、标注错页进前 3 的次数、空结果数、延迟和降级次数。
- 再用**冻结组**确认没有退化。冻结组只用来确认，不用来调参。评测集的构建方法见[记忆评测教训](memory-eval.md)。
- 门槛：开发组达到第 1 步的判定线，冻结组不退化；接受的退化要写明原因。

## 5. 上线门槛

- **负责人批准**。旧的发布授权不自动覆盖新改动。
- **保留紧急关闭开关**，写清回滚步骤和回滚后怎么确认恢复。
- **发布顺序：先后端，后面向 Agent 的说明或技能包**。说明先于后端上线，Agent 会照着还不存在的行为去用。
- **上线后用生产重跑评测集**相关题和正例，按第 4 步的口径报读数。
- **读回实际运行的版本**。响应里没有版本标识时，用部署平台读回每个集群的版本和健康实例数。
- 门槛：批准记录、开关、生产重跑读数、版本读回四样齐全，才算上线完成。

## 6. 留痕

- 结论和证据写回内部的里程碑记录。
- 能公开的部分写成公开实验或教训，结论只用 Works / Does not work / Inconclusive，内部数字只写比例。
- 新的 bad case 原句补进评测集**开发组**，不进冻结组；补完核对两组页 ID 不重叠。

## 7. 常见坑

- **小模型只看摘要下的结论要对照代码复核。** 现象：只看页首几行、不对代码、不二审的一轮判定整体是错的。做法：判定方法先过第 3 步的门槛。
- **「显示完成」不等于成功。** 现象：外层任务在全部子任务失败时仍显示完成。做法：验收看子任务结果和实际产出。
- **计划里写的隔离环境不一定真隔离。** 做法：用请求 ID 查请求实际落在哪个集群，再下结论。
- **提交人不能自己审核发布。** 做法：提单前确认另一位审核人。
- **Agent 会话压缩后换账号续跑会失效。** 做法：长任务的状态写进文件，从文件续接。
- **一个数字不要归给两件事。** 做法：召回、内容、采纳分开度量。

## 没覆盖的

- 这套流程只走过一轮，没有在第二轮迭代里验证。
- ≥90% 的放量线和「几十页」的试点规模是经验值。
- 第 7 步部分条目来自负责人归纳，这里没有附逐条的事故记录。
