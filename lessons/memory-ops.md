# 教训：记忆后台管线的运维

来源：一个内部场景里约一天的运维排查，样本很小（几个到几十个空间），只留不依赖内部背景的通用结论。关联 [plan](../plans/team-memory-quality/README.md) 与 [#38](https://github.com/yaodiff/memory-lab/issues/38)。条目格式：现象、原因、做法。

下文三条都发生在同一类后台管线里：按空间领取待处理的来源，调用模型把来源整理成记忆页，再由夜间任务做整合。三条的共同点是：账面看起来正常，实际没有在做事。

## 外层任务在所有子块失败时仍显示「完成」

- **现象。** 夜间整合把一个空间的工作切成若干块，每块单独调用模型。一次审计发现：窗口内每个空间的外层记录都是「完成」，但实际开跑的块成功数为 0，块都是超时无结果，其中多数在记录里能看到限流（HTTP 429）。（来自内部小样本。）
- **原因。** 块内的失败被捕获、记录后返回「未成功」标志，不再向外抛异常。外层只按「有没有抛异常」定状态：正常返回统一记为完成，只有异常才记失败。所以只要块级失败被收住，外层就是完成。
- **做法一：状态由实际运行的块算出来。** 全部成功记完成，有成功也有失败记部分失败，已运行的块全部失败记失败。不要用「函数有没有返回」代替「事情有没有做成」。
- **做法二：零块要单独定义。** 没有待整理的块、或来不及开始，都是零块。零块记完成，并沿用原来的「锁被占用，跳过」回执，不要把零块算成失败。
- **做法三：失败数和原因随状态一起落账。** 失败块数和每块的失败明细（范围、错误）写进已有的运行账本载荷、维护日志和本地报告，日志带上空间和运行 ID，三处能互相对上。不新增存储。
- **做法四：新状态值先核对下游。** 状态字段有长度上限，新增的取值要核对存储定义和读取方。同时核对调度：全失败会被现有的夜间补跑识别（有每日补跑次数上限，到上限进告警汇总），部分失败仍靠页级的待处理与重试承接。
- **别把超时都归给限流。** 现象：限流拒绝和超时在同一个窗口里同时出现。原因：缺少逐块与网关请求的配对，只能说两者同窗，不能说因果。做法：超时与已捕获的限流分开记录，归因粒度写明。
- **验收要说清哪个分支被真实流量验证过。** 修复用单测覆盖了全成功、部分失败、全失败、零块四种情形，测试走真实的维护入口，账本用本地假实现。发布后一段时间里生产只出现了零块样本，全失败分支还没有自然样本。做法：写明哪些分支只有单测、哪些有线上读数，并事先写好下一次要看的观察点。
- **状态：** 修复已合入并发布，发布后读回了实际运行的版本。非零块分支的生产验证在写作时尚未完成。

## 领取队列里某一来源积压，把其他来源饿死

- **现象。** 三个空间的会话积压从个位数到数百条不等，群聊、笔记、纠正等其他来源的最早未处理版本都已停了一两天。同一时间窗内，这三个空间的构建记录全是会话，其他类型一次都没有。（来自内部小样本。）
- **原因一：领取排序。** 领取查询按「会话优先，再按变更时间」排序，只取批额的若干倍（约 8 倍）作候选窗口，再逐条检查是否到时，拿到批额就停。到时的会话足够多时，窗口里全是会话，别的来源排在窗口之外。在这三个空间里，第一条非会话候选都排在序列靠后的位置（其中一个空间在前百余位里一条都没有），批额小时根本进不了窗口。会话少的空间也一样：会话排序在先，批额为个位数时照样被会话用完。
- **原因二：并发长期接近满载。** 绝大多数采样点的构建槽都是满的，分到每个空间的批额很小，小批额下窗口也小，饥饿更重。
- **原因三（独立于排序）：类型白名单。** 其中一种来源（代码）对这三个空间根本没有开放，在查询的类型过滤阶段就被排除了。它的积压与排序无关，不能用排序修复去解释。
- **做法一：有会话积压时，为非会话留一个名额。** 会话占满旧的候选窗口、或到时的会话多于本批名额时，额外发一次只看非会话来源的查询，沿用同样的状态过滤、租约、类型白名单和到时判断，用同样的条件更新取至多一个租约；其余名额仍走旧队列。没有会话积压时保持旧行为。
- **做法二：默认关闭，按空间名单开启，回滚就是清名单。** 先在预发环境验证，再在生产先开一个空间。验证看自然流量：前后各取一段时间，比较非会话的新增构建、同类型最早未处理时间、会话处理量和领取查询时延。
- **取舍要写明。** 额外多查一个候选窗口；批额为 1 时唯一的名额可能给非会话，老的笔记可能先于群聊被处理。把「到时」判断下推到查询里也不够，因为到时的会话本身就足够多。
- **先分清是哪种停滞。** 现象：来源从一两天前起就没被领取，而模型限流是之后才出现的。原因：限流与领取排序是两个问题，时间线可以拆开。做法：先对齐时间，再决定是修限流、修排序，还是修白名单。起初「可能是领取排序」只是猜测，是用只读查询复现候选窗口后才确认的。
- **领取日志要能还原候选。** 现象：历史日志只有请求体大小，调试项也只记「想领多少、领到多少」，没有候选类型分布，只能用当前数据重算。做法：重算的结果要标成快照，不当作历史审计；以后在日志里记候选窗口的类型构成。
- **状态：** 修复以草稿提交评审，未合并、未部署，效果未经生产验证。

## 只写不读的旧副本，停写前先查三件事

- **现象。** 迁移到新链路之后，旧的向量副本仍在持续写入同一批来源。想停写省成本，但存量审计显示：不是所有空间都可以停。
- **原因。** 「新链路已经上线」不等于「每个来源、每个空间都被新链路接住了」，也不等于「没人读旧副本」。
- **做法：逐空间核对三个条件，缺一个就不停。**
  1. **有覆盖来源。** 新链路覆盖了这个空间的全部来源。例子：有的来源被新链路的名称规则排除（如测试群），旧副本停写后，这些消息不会再进入任何记忆链路。
  2. **处理水位在推进。** 要在新链路上实测，看停写之后新来源确实被构建成功、处理水位在前进，不能只看「新版本一直在登记」。例子：几个空间登记仍在继续，但待处理来源多日没被领取，水位停滞；此时保留旧写入也补不上缺口，只保留了回滚素材，没有业务兜底。
  3. **没有读方。** 分开核对：常规召回（按生产返回条目统计，取一个月窗口，看最后一条返回的时间）、其他服务的代码引用、治理或周报类的读取、前端展示。例子：停写后界面上的「最近同步时间／累计条数」会不再变化。治理用途的读取不等于业务读方，但要单独列出，不能默认忽略。
- **结果（来自内部小样本）。** 逐空间核对后，只有约八分之一的空间可以直接停写，约八分之三待在新链路读回水位后可停，约一半不可停（一个缺来源覆盖，其余水位停滞）。
- **用名单，不用全局开关。** 全局开关无法豁免个别空间，打开就会停掉还不能停的；它还会自动覆盖以后新绑定的来源，而新来源可能根本没有被新链路接住。名单可以逐个空间回滚。全局开关的前提是：所有仍在写的空间都已进名单，且新绑定的来源能保证被覆盖。
- **停写后观察一个完整扫描周期。** 读回旧写入量为 0、新链路对新消息的处理水位在推进；停写生效的时间点要记下来，作为观察起点。停写是可回滚的，清理存量另需单独依据：存量里有的目录仍被召回、溯源或回滚依赖。
- **缺口要写明。** 提供方侧的访问日志、外部评测平台的任务、临时脚本的读取，业务侧拿不到；没有账单也就给不出实际节省的金额。读方结论只能写到「业务侧没有」。

## 让纠正当天能被本人搜到

- **Works**。显式保存的用户纠正以带来源和「未核实」标记的个人短记录供本人检索，正式页仍由原有后台流程生成。内部生产已启用空间的探针在建页前命中。修复后台处理后短记录漏召回的问题后，同一条没有产出正式页的记录由重复探针全部漏掉变为全部首位命中。未开启的对照空间均未返回该记录。
- **Inconclusive**。验证使用显式保存和单一授权身份。真实会话是否会主动保存、同空间其他授权成员能否读到，以及扩围后的表现仍待验证。全量开关仍待审核。
