# 读 Meta 的 Self-Improving Memory：让模型改自己的记忆提示，再蒸馏进权重

[English](04-self-improving-memory.en.md) · 中文

> 草稿 v1。论文的数字都引自原文；「我们」的观察来自一个团队记忆系统的内部实践，只写粗粒度描述，样本小，场景是编程 Agent 的团队约定。配套的小实验见 [E004](../experiments/E004-meta-optimized-memory-prompts/README.md)，数据全部合成。

## 一句话

Meta FAIR 的博客 [Self-Improving Memory: Meta-Optimization and Harness Distillation for Continual Learning Agents](https://facebookresearch.github.io/RAM/blogs/self_improving_memory/)（Tong Chen、Jason Weston 等，[项目源文件](https://github.com/facebookresearch/RAM/tree/main/projects/self_improving_memory)）2026-11-10 首次提交到仓库，本文读的是 2026-11-17 的修订版。截至 2026-11-20 我们只找到博客，没找到 arXiv 论文，下文以博客为准。

它做两件事：先让模型按任务**改写自己的记忆读写提示**（LOAD / OFFLOAD），挑分最高的留下；再用改写后的提示跑出轨迹，**把提示换回通用版**拿去微调，让模型在通用提示下也会这样用记忆。读数：通用提示 36.1，改写后 56.0（人写最佳 44.6）；蒸馏后通用提示 43.1，对照组 37.6。

我们的看法：第一步（按任务搜提示）的证据扎实但有「在同一批任务上选、在同一批任务上报」的味道；第二步的增益是真实的，但只拿回了第一步增益的约三分之一。对团队记忆最有用的不是「自动搜提示」本身，而是它搜出来的那些写法：**先读护栏再读数据、事实带确认状态、失败写成 IF→THEN、有索引而不是一个越写越长的文件**。

## 它要解决什么问题

一个 Agent 连续做很多相关子任务，每个子任务开一个空上下文，唯一能带过去的是一个记忆目录（Markdown 文件，用文件工具读写）。问题是：**记什么、怎么组织、什么时候读回来**，今天全靠人写的提示决定，而没有一种写法在所有任务上都最好。

博客的预实验（Figure 2）在 Continual Learning Bench 的三个任务上（Database 数据库问答、Codebase 代码修复、Spectrum 光谱分析）比了通用提示和四种人写的记忆策略（摘要、检索、技能库、假设追踪），每个任务的最佳策略都不同。这和 Continual Learning Bench 原文的结论一致：专门的记忆系统不能解决「跨实例复用知识」的问题（[Asawa et al., 2026](https://arxiv.org/abs/2606.05661)）。

所以它主张：让模型自己发现记忆策略，再把策略练进权重。

## 方法

### 通用 harness

- 记忆目录开始是空的，贯穿整个任务流。
- 每个子任务做完，OFFLOAD 提示让模型更新记忆；然后清空上下文。
- 下一个子任务开始前，LOAD 提示让模型去读记忆（可以马上读 README，也可以做到一半再读）。
- 通用版的 LOAD / OFFLOAD 故意很短，原文 Figure 1：LOAD「Read your memory directory.」，OFFLOAD「Update it. What to keep is your decision.」

### 第一步：harness 优化（Discover）

一个 meta agent 读任务 Agent 的轨迹和得分，改写 LOAD / OFFLOAD，外层循环负责评估和保留：

1. 初始池：四个人写的种子（摘要、检索、技能库、假设追踪）。
2. 每个候选把整条任务流跑 N 次（例如 5 次），记录轨迹、子任务得分和最终记忆目录。
3. 按平均分排序，取前 P 个（例如 4 个）当父本。
4. meta agent 先逐个子任务总结、再逐条运行分析、最后跨运行汇总，写出改写后的 LOAD / OFFLOAD，加回池子。

重复若干轮，取分最高的存活者。原文写的是「在 meta agent 看不到的 holdout 上取平均分最高」。

**搜出来的提示长什么样**（原文 Figure 1，Database 任务）：

> LOAD：先读 GUARDRAILS.md，再读 SCHEMA.md。回答前检查价格单位和时间戳类型；查询不超过 5 次。
> OFFLOAD：记下每个分组的价格单位和时间戳格式（CONFIRMED / UNTESTED）；失败记成 IF→THEN 规则。

Codebase 任务的演化（Figure 7）更能说明问题：

| 版本 | LOAD / OFFLOAD 要点 | 分 |
| --- | --- | --- |
| 通用 | 读记忆；自己决定记什么 | 33.5 |
| 人写「摘要」 | 读唯一一份滚动摘要；把本次教训折进去 | 34.3 |
| meta 报告 | 每次运行都只有一个线性增长的文件，Agent 还是重新找仓库、用 sed 改坏文件、被本来就挂的测试卡住 | — |
| 第 1 轮较好版 | 复用记下的仓库路径，先复现 bug、提交前跑全量测试；记速查、坑规则和修复日志，**每次失败后加一条规则** | 52.2 |
| 第 1 轮较差版 | 记仓库根和测试命令；记忆封顶 4000 字，**只留最近两次修复** | 36.6 |
| meta 报告 | 只有一个追加写的文件、没有「症状 → 修法」的索引，Agent 重复探索已解决的问题 | — |
| 第 2 轮最佳 | 读简短 quickstart 和「症状 → 修法」索引，复述匹配的修法和规则再照做；quickstart 封顶，一修一文件，失败后合并重复 | 55.7 |

### 第二步：harness 蒸馏（Demonstrate → Distill）

1. 用每个任务分最高的提示，让基座模型在训练子任务上跑，记录每次调用的提示、回复、推理、工具调用和工具返回。
2. 在记录里把优化后的 LOAD / OFFLOAD **原地替换成通用版**，回复保持不变。能这么换，是因为优化版只规定了一种记忆设计，而通用版把选择权留给模型，所以这些行为在通用提示下也「说得通」。
3. 三个任务的样本合在一起，只在助手 token（含推理和工具调用）上算 loss，按任务的监督 token 数归一化，让每个任务权重相同。LoRA rank 64，只加在注意力投影层。

meta agent 和任务 Agent 是同一个模型（Kimi-K2.6），所以是「模型学自己发现的记忆技能」。

## 局限

1. **「最佳」是在被评测的候选里挑的**。原文自己写明：人写种子和优化后提示都按任务分选出，所以这些是「被评测候选中观察到的最好分」。它说用 holdout 选，但没有给出「选完以后在一个从没参与选择的新任务流上再报一次」的数。56.0 对 44.6 的差距里，有多少是选择带来的乐观偏差，读不出来。
2. **只有三个任务、一个模型**。meta agent 和任务 Agent 都是 Kimi-K2.6；没有换模型、换任务族的结果。
3. **蒸馏只拿回一部分**。优化后提示比通用高 19.9 分，蒸馏后只比不微调高 7.0 分；而且原文说这 7.0 分是描述性的，因为基座模型是单独评测的。有配对种子的对比是 43.1 对 37.6（+5.5）。Database 上「用通用轨迹微调」反而比不微调低（31.6 对 32.3）。
4. **蒸馏增益来自哪里没拆开**。原文写「我们推测部分来自更好的记忆组织和检索，也有解题行为，要分离这个机制需要直接的行为分析」。也就是说：微调后的模型更会用记忆，还是只是更会做这三个任务，目前没证据区分。
5. **搜索很贵，命中率低**。每个候选要把整条任务流跑 5 次；44 个改写里 37 个白跑。没给 token 或成本。
6. **替换提示的前提是「行为在通用提示下也说得通」**。这是一个论证，不是一个检验：没有测换回通用提示后轨迹是否仍是模型在通用提示下会产生的分布。

## 我们该不该信

- **信「没有一种人写记忆策略通吃」**：它的预实验、Continual Learning Bench 原文和 [Yang et al., 2026](https://arxiv.org/abs/2604.11610) 方向一致，我们在团队记忆里也看到不同空间、不同任务类型适合的写法不同。
- **信「按任务改写提示能涨很多分」，但打个折**：方向可信（Codebase 的演化过程讲得通，失败也照实报了），幅度要等「选完再在新任务流上测」的数字。我们的小实验 [E004](../experiments/E004-meta-optimized-memory-prompts/README.md) 就是去测这一点。
- **对「蒸馏进权重」保持观望**：+5.5 分有配对对照，是真实的；但我们不训练模型，这一半对我们只有间接意义——它说明「好的记忆行为」可以从提示里搬出去，对我们来说是搬进 Skill 和整理流程的默认写法。
- **最值得拿走的是搜出来的写法本身**，它们和我们踩过的坑高度重合，见下一节。

## 和我们的做法对照

我们的场景：多人团队里的编程 Agent，记忆是一个 Wiki（规范、决策、经验、实体、事件），由一个后台整理流程从会话里提炼；Agent 通过一个 Skill 学会什么时候搜、怎么用。和论文最大的不同：**论文的读写提示同时管「写」和「读」，而我们的写由后台提炼提示负责，读由 Skill 负责，两头分开调**。下面按四个点对照。

### 1. 读取顺序：先护栏，后事实，用之前复述

| 论文搜出来的 | 我们现在 | 能借鉴的 |
| --- | --- | --- |
| Database：先读 GUARDRAILS.md 再读 SCHEMA.md，回答前检查价格单位和时间戳类型 | 开工先用需求原话搜一次，再只搜规范一次；中途在决策点再搜 | 「先护栏」我们有（单独搜规范），但顺序是先任务后规范。可以试把「这一类操作的禁止项」放在最前面读 |
| Codebase 最佳：读 quickstart 和「症状 → 修法」索引，**复述匹配的修法和规则，再照做** | 交付前对照读过的规范逐条核对 diff | 我们的核对在动手之后。[第 01 篇](01-three-gates.md)里漏得最多的是「用上」：读了全文却只照做一部分。把「复述匹配的规则」挪到动手之前，是一个便宜、可测的改动 |

### 2. 提炼提示：索引、一事一页、失败后合并

| 论文搜出来的 | 我们现在 | 能借鉴的 |
| --- | --- | --- |
| 一修一文件；封顶的 quickstart；失败后合并重复 | 一页只讲一个问题；后台整理会合并同一经验 | 已经同向 |
| 「症状 → 修法」索引表 | 规范有按类别的目录；经验页没有按报错症状的索引 | 给经验页加一个按「报错原文 / 现象」的索引，正好对应 Agent 中途「拿报错去搜」的那一步 |
| 较差版：封顶并只留最近两次修复，36.6 分 | 我们的整理也出过「合并时丢事实」的问题 | 印证：为了控长度砍掉历史细节，比不控长度更伤 |

### 3. 失败经验的适用范围

论文的 OFFLOAD 要求「每次失败后加一条规则」，写成 IF→THEN。我们的提炼提示也要求经验页的做法用 IF/THEN 写清分支。但我们踩过的坑是：**一次失败被写成永久规则，适用范围被写宽，误导后面的任务**（[#19](https://github.com/yaodiff/memory-lab/issues/19) 在测这件事）。IF→THEN 的好处恰恰是逼着写出条件：IF 那半句就是适用范围。能借鉴的是把 IF 写成**观察到的条件**（哪个系统、哪类报错、什么前置状态），而不是推断出的泛化条件；只有一次来源的，IF 里保留「在 X 情况下观察到一次」。

### 4. CONFIRMED / UNTESTED 状态标记

论文 Database 的 OFFLOAD 要给每条事实标 CONFIRMED 或 UNTESTED。我们的决策页有状态（已确定 / 已否决 / 已废止），但**经验和实体里的单条事实没有「验证过没有」的标记**：一条从对话转述来的命令和一条跑通过的命令，在页面上长得一样。Skill 里有一条补救规则：「含命令或路径的条目先跑一遍再采纳」，但 Agent 读页时分不出哪些需要先跑。

这里有一个要小心的冲突。我们的提炼提示**刻意不让**经验页写当次的验证结果和进度（「已部署验证」「已通过多少用例」），因为抽查发现这类状态很快过期、读者会当成现状。论文的 CONFIRMED 标的是**事实本身的依据**（这个分组的价格单位被反馈证实过），不是任务进度。所以能借鉴的是标「依据的性质」：命令跑通过 / 对过代码 / 只是会话里有人这么说，而不是「某天验证通过」。Skill 只要求对后一类先核对；被纠正过的条目回退成「只是转述」。

### 5. 自动改提示本身

论文里 44 个改写有 37 个没赢，Database 和 Spectrum 第一代之后再没涨。这和我们改 Skill 写法的经验一致：内部小样本里，最好的一版也只在少数题上和基线拉开差距。**自动改写便宜，评测和筛选才是成本**。如果要把 meta agent 用在我们的 Skill 或提炼提示上，前提是有一套冻结的、和改写者隔离的评测集，并且在选完之后再到一批没参与选择的题上报一次。

## 我们的小实验：E004

想测的是论文没给的那个数：**在一个世界上选出来、冻结的记忆提示，到没参与选择的新世界上还赢不赢通用版**。做法是合成的单位推断题（分组的价格是「分」还是「元」、数量是「件」还是「打」，只能从反馈推），小模型同时当任务 Agent 和 meta agent，判定线运行前写死。细节和全部读数见 [E004](../experiments/E004-meta-optimized-memory-prompts/README.md)。

| 组 | 3 个新世界的平均准确率 |
| --- | ---: |
| 无记忆 | 0.17 |
| 通用 | 0.57 |
| 人写「摘要」 | 0.57 |
| 照搬论文 Database 提示 | 0.43 |
| 搜索选出的（= 通用提示再跑一次） | 0.36 |

- **4 个 meta 改写没有一个赢过最好的种子**，选中的就是通用提示。和论文 44 个里 37 个没赢同向。
- **同一份提示跑两次差 0.21**，单个世界差 0.29。在这个规模上，噪声比论文报告的任何一项提升都大。按预设判定线这次记「不行」，但更准确的读法是：这个规模测不出 meta 优化的效果。
- **照搬论文搜出的提示没有迁移**，翻转后的题全错。
- 一个和团队记忆直接相关的失败：一次运行在第 1 题后把「价格都是分」写成全局规则，之后 13 题答错 12 题，记忆里记下了每次反证，规则却一直没改。这就是上面第 3 点说的「一次观察写成永久规则」，而且在同一份提示下是随机出现的。所以光靠提示措辞不够，IF 条件和依据状态最好是记忆格式的一部分。

## 小结

| 论文的发现 | 证据强度 | 对团队记忆 |
| --- | --- | --- |
| 没有通吃的人写记忆策略 | 强，多方一致 | 同意 |
| 按任务自动改写提示涨 11～20 分 | 方向可信，幅度含选择偏差；我们的小实验测不出 | 只拿它搜出的写法，不急着上自动搜索；要上先有冻结评测集 |
| 蒸馏把一部分增益搬进权重 | +5.5，有配对对照 | 我们不训模型；等价做法是写进 Skill 和提炼提示的默认值 |
| 搜出的写法：先护栏、复述再做、依据状态、IF→THEN、症状索引 | 案例 | 四个可测的改动：动手前复述规则、先读规范、IF 写观察条件、标依据性质 |
