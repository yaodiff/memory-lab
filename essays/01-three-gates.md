# 团队记忆的三道关：写对、搜得到、用得上

[English](01-three-gates.en.md) · 中文

> 草稿 v0。标【待审批数字】的数据来自内部实践，公开前要么过审，要么换成本仓库开源复现的数字。

## 一句话

给编程 Agent 做团队记忆，最该问的不是“它能不能记住”，而是“**它还会不会被同一个人、为同一件事纠正**”。按这个问题去看，一条团队约定要连过三道关：**写对、搜得到、用得上**。每道关失败的样子都不同，修法也不同。

## 为什么不用现成的 benchmark

LongMemEval、LoCoMo 这类评测，是在长对话里埋一个事实，之后再问。它们测的是**事实召回**：用户上周说过喜欢什么、某件事发生在哪天。

团队记忆里真正值钱的是另一类东西：

- **约定**：“这个仓库提交前要跑 X 检查”“查调用链用某个工具，不要自己 grep 日志”。
- **决策**：“首期先用方案 A，二期再换”。
- **经验**：“这个报错其实是凭证过期，不是网络问题”。

这些东西不会被直接问到。它们只在 Agent **正要做某一步**时才派上用场，而且没有人提醒 Agent“现在该想起它了”。所以要换一个评测单位：不用“一个问题”，改用“**一次纠正**”。

## 纠正是免费的监督信号

用户纠正 Agent（“不对，这里要先……”“我们不这么做”），本身就说明了三件事：

1. 这里有一条团队约定（或者个人偏好，要分开）。
2. Agent 当时没照做。
3. 纠正之前那一刻，就是这条约定本该生效的决策点。

把每一次值得记的纠正拿来对账，问三个问题：

| 对账结果 | 含义 | 是哪道关的缺口 |
|---|---|---|
| 页面早就有，仍被纠正 | 记忆里有，Agent 没用上 | 搜得到 / 用得上 |
| 漏学或只写了一半 | 纠正发生过，记忆里没有或不完整 | 写对 |
| 事后学会 | 纠正之后才写进记忆 | 正常，下次再看有没有生效 |

这张表每晚都能自动跑出来，比任何人工标注都便宜。要注意的是：**对账判定本身方差很大**。同一批判成“漏学”的纠正，换一个模型重判，会有相当一部分被改判【待审批数字】。所以至少要用两个独立判官，报一致率，分歧逐条看。

## 第一关：写对

常见的写错有四种：

- **把进度写成决策**：“今天先改了 A”被写成“团队决定用 A”。
- **把一次性要求写成规则**：用户这一次说“先别跑测试”，被当成团队约定。
- **丢掉适用范围**：“首期”“未发布的版本”被当成无关细节删掉，结论变宽。我们试过加一个自动检查器来“清理决策页”，盲评时旧版反而胜多负少，原因就是检查器把范围删了。
- **漏掉长任务中途顺带的一句纠正**：抽取器按任务主题建页，跟主题无关的环境、协作约定（比如“本地不要起数据库，用共享测试环境”“给用户的链接要能直接打开”）就被丢了。

还有一个反直觉的收益：**能从代码直接读出来的事实，不要存**。存了只会过时，还会和代码打架。冲突时一律以代码和已合入的改动为准。

## 第二关：搜得到

这是我们花时间最多、也最意外的一关。

先说结论：**排序基本没问题，问题出在 Agent 问的是什么**。

- 拿纠正的摘要直接当 query 去搜，对的那页进前 3 的比例很高【待审批数字】。这说明只要搜对了题，排序是够用的。
- 但 Agent 真实发出的 query，是它**手头的任务**（比如“把这个分支的改动提交并推上去”），而约定写的是**这一类步骤怎么做**（“提交前要跑什么检查”）。两边说的根本不是同一件事。
- 在服务端改写 query（取动作短语、改写成“这一步团队怎么做”）一条都救不回来，因为 Agent 的 query 里压根没有这层意思。
- 改 Skill 文案、压缩结果、加索引，在“纠正前那一刻重放”里逐题几乎没有差别：搜得到的那些题怎么改都搜得到，搜不到的怎么改都搜不到。

我们想试的方向是**步骤级检索**：让 Agent 在搜索时多写一句“我接下来要做的这一步”，按这一步再搜一路，和原结果合并。离线预检能多救回一部分“这类事团队怎么做”的约定，但领域决策救不回。这是第四篇文章的主题。

## 第三关：用得上

就算读到了全文，Agent 也不一定照做。在我们的样本里，“读了全文却没完全照做”是最大的一块【待审批数字】：页面明明写了漏掉的那一点，Agent 却自己另加了设计，或者漏了细节。

所以要分层埋点，至少分到这几层：**有没有搜 → 搜到对的页没有 → 读了全文没有 → 照做了没有**。只看一个“采纳率”，你不会知道该修哪里。

## 最重要的一个坑：同会话泄漏

评测的做法是：从真实会话里取纠正之前那一步，分别在有记忆和无记忆两种条件下让 Agent 出方案，再判方案违不违反约定。整体看下来，有记忆时违反率下降得很明显【待审批数字】。

后来逐个 case 看才发现：其中不少 case【待审批数字】，对应的页面**就是从这次会话本身学出来的**，有的甚至是纠正之后才更新的。有记忆的那一组，等于提前看到了答案。只看页面来自别的会话、纠正后也没更新过的干净 case，**收益几乎为零**。

这一条值得单独写一篇（第三篇）。结论很简单：**评测团队记忆时，必须按页面来源切掉同会话的 case**，否则收益会被明显高估。

## 还有一类事故：管道静默坏掉

很多“搜不到”的根因根本不在检索算法：

- 存储层悄悄改了写入路径，读和删却没跟着改，结果召回丢页、清理时误删。
- 消息接收断了好几天，没人发现。
- 环境变量没展开，一批记忆写进了空空间。
- 凭证失效时返回了空结果，被当成“真没有”。

所以检索**空结果必须带原因**（真没有 / 被挡住 / 坏了），写完要回读做一致性检查。

## 小结

| 关 | 先查什么 | 不要先做什么 |
|---|---|---|
| 写对 | 适用范围有没有保住、中途纠正有没有漏 | 加检查器“清理”页面 |
| 搜得到 | Agent 在决策点有没有搜、query 是任务还是步骤 | 调排序、改文案 |
| 用得上 | 读全文后照做的比例 | 只看一个采纳率 |
| 评测 | 切掉同会话 case、用双判官 | 拿整体对照的收益下结论 |
