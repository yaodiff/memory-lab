# 用团队记忆的一线数据读 Anthropic 的「记忆组件」

[English](02-reading-the-components.en.md) · 中文

> 草稿 v1。文中「我们」的数字来自一个团队记忆系统的内部实践，只写比例或粗粒度描述，不放原始数据和样例；样本小，场景是编程 Agent 的团队约定，不代表别的场景。Anthropic 的数字都引自原文。

## 一句话

Anthropic 在 2026-11-06 发了 [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)，把 Agent 记忆拆成几个组件：会话里写笔记、注入上下文的顶层、wiki 这类表示，以及离线整理（dreaming）。拿[第 01 篇](01-three-gates.md)的三道关（写对 / 找到 / 用上）去对：

- **写对、找到**：它的结论和我们看到的大体同向，只是落点不同。
- **用上**：它只用一句话带过，而在我们的数据里，这恰恰是漏得最多的一关。
- **整理**：它讲的失败模式，我们几乎都踩过，还多踩了几个。

## 先说清这是什么样的对照

- **场景不同**。它的实验是 CL-Bench 的数据库问答、玩 Pokémon、在文档库上答题和写法律 brief：单个 Agent，有可核对的标准答案。我们是多人团队里的编程 Agent，监督信号是人的纠正，没有标准答案。
- **样本都不大**。它的部分实验是 25 道题、24 道题这个量级；我们的更小，几十道题、每组跑两遍。
- 所以下面写的是「方向对得上的地方」和「对不上的地方」，不是复现，也不是评判谁对谁错。

## 第一关：写对 ↔ 「记忆是一种预测」

**它说了什么**

- 写下一条规则，就是在预测这个模式以后还会用到。
- Pokémon 的对比：早期模型什么都记，几百个文件，记的东西随游戏状态不停过时，最后花在翻记忆上的时间比玩游戏还多；新模型只记屏幕上读不出来的东西（策略、计划、验证过的规则），文件少得多，走得远得多。
- **告诉模型记忆是干什么的，而不是规定怎么写**。在 CL-Bench 上只告诉模型有一个记忆目录，强模型就会用；给它们加上「只记失败」这种固定规则，记忆带来的提升反而丢掉一大块。反过来，对较老的模型，提示「答题前先读记忆、并验证自己的猜想」能让分数接近翻倍。

**我们对得上的**

- 01 篇里那条「能从代码直接读出的事实不要存」，和「不记屏幕上读得到的东西」是同一个道理：存了只会过时，还会和真实状态打架。
- **改规定性的文案不是杠杆**。我们在 Next-step Replay（从真实会话切到被纠正前那一刻，重放给 Agent）上比较了几版使用说明 Skill 的写法：页首加照做要点、压缩返回结果、加索引。49 道真实题、每组跑 2 遍，最好的一版和基线比，好 1 题、差 1 题，其余全部持平；基线自己两遍结果完全一致。

**对不上、要说清的**

- 它说的是「怎么写记忆」的指令，我们改的主要是「怎么用记忆」的指令（什么时候搜、query 怎么写、结果怎么呈现）。两边都指向「规定性指令不是杠杆」，但对象不同，不能互相当证据。
- 它看到的是固定规则**掉分**，我们看到的是**没差别**。我们的解释不是「模型已经会自己判断」，而是瓶颈根本不在这里（见第二关）。
- 团队场景多了一层它没碰到的问题：写记忆的和用记忆的不是同一个会话，常常也不是同一个人。「预测以后会用到」在这里还要预测**谁、在哪一步**会用到，所以**适用范围**（「首期」「未发布的版本」）比结论本身更重要。01 篇里检查器把范围当细节删掉、结论被写宽，就是这一类失败。
- 这 49 道题里有相当一部分是评测集自己没对齐：被纠正的事和纠正前最后一句用户话说的不是一件事。清洗后两项都过的只剩一半左右。所以「没差别」只能说到「在这批题上测不出差别」为止。

## 第二关：找到 ↔ 「注入层要小」与「wiki + 搜索」

**它说了什么**

- 记忆是分层的：顶层在每个会话开头直接注入，下面的层按需读或搜。顶层要小，因为它占 token、错的笔记会被带进每一个会话，而且加载了也不保证照做。Claude Code 的 auto memory 只加载 `MEMORY.md` 的前 200 行或 25 KB，当作索引，告诉模型自己知道什么、去哪找。
- 在一个约 35 万个文件的内部文档库上：wiki + 搜索的得分随 wiki 变大从 54% 升到 61%；只用搜索 53%；只用 wiki 最好 48%；wiki + 搜索每题还省约 2 万 token。需要跨多份文档拼答案的题，wiki 帮助很大（87% 对 73%）；单份文档就能搜到答案的题，wiki 没有明显收益。

**我们对得上的**

- 我们默认**不注入**：一个使用说明 Skill 加一组搜索工具，什么时候搜由 Agent 决定。相当于把它的顶层压到几乎为零，全靠下层检索。
- **搜对了题，排序是够用的**：拿纠正的摘要直接当 query，对的那页进前 3 的比例很高。
- **搜不到，是因为 query 对不上**。Agent 在决策点搜的是手头的任务（「把这个分支的改动提交并推上去」），而规范写的是「这一步怎么做」（「提交前要跑哪些检查」）。上面那 49 道题里，有一批题每一组每一遍都搜到，另一批每一组每一遍都没搜到：结果由「这一刻的自然 query 能不能对上页面」决定，和 Skill 怎么写无关。服务端改写 query 也救不回来，因为 query 里压根没有这层意思。

**这和它的分层怎么接**

- 它的 wiki + 搜索之所以比只搜好，一个解释是 wiki 给了 Agent 一张地图，Agent 不用先知道该搜什么。【推断】这正打在我们的痛点上：我们的失败不在排序，而在 Agent 不知道「这一步有约定可查」。
- 但它的实验是问答和写 brief，题目本身就是 query。编程 Agent 的团队约定要在**没人问**的时候被想起，这一层它的实验没有覆盖。
- 顶层注入这条路在团队场景下很贵：一个活跃团队积累的规范远远塞不进 200 行，硬塞又会撞上「越长越不照做」。我们更想试的是第三条路，**步骤级检索**：让 Agent 搜的时候多写一句「我接下来要做的这一步」，按这一步另搜一路，和原结果合并。离线预检能多救回一部分「这类事团队怎么做」的约定，领域决策救不回。细节留给第 04 篇。

## 第三关：用上 ↔ 「加载了不保证照做」

**它说了什么**

只有一句，出现在讲注入层的地方：加载一条笔记并不保证 Claude 照着做，Claude Code 的文档也提醒，指令文件越长，遵循度越低。文中另一处相关的是较老的模型「经常不去读记忆目录」，但那是读没读的问题，还属于第二关。

**我们看到的**

- 在几十个真实纠正 case 上，我们把每个 case 卡在哪一层拆开：没搜、搜了没搜到对的页、读了全文但没完全照做、照做了。**最大的一块是「读了全文但没完全照做」，接近四成**，比「没搜」和「没搜到」都多。
- 把对的页直接摆在 Agent 面前、不用它去搜，**仍有约五分之一的方案违反约定**。
- 「没完全照做」主要是两种样子（下面是改写过的合成例子，不是原始案例）：
  - **漏细节**。规范写「改公共接口要同时改调用方和文档，一起提交」，Agent 改了接口和调用方，文档没动。
  - **另加设计**。规范写「这个仓库的配置变更走现有的加载器，不要新加读取路径」，Agent 读到了，然后「为了更清楚」另写了一个小封装。

这一关在它的文章里只占一句，我们觉得原因之一是它的实验大多有标准答案：笔记对了，照着做就能得分，「读了但只照做一半」不太会单独冒出来。团队约定不一样，一条规范常有好几个要点，Agent 很容易做对主干、漏掉其中一点。【推断】

**为什么这一关最难测**

1. **没有天然信号**。搜索有日志，读页有日志，「照做」只体现在之后的行为里，而且常常是部分照做。让 Agent 自己回报「用了这条」，只能说明它读过，说明不了照做。
2. **判定要拆到要点**。一条规范有几个要点，「照做」就要逐点对；只判整体对或错，会把部分照做吞掉。判官本身方差也大：同一批判定换个模型重判，会有一部分被改判。所以至少要两个独立判官，报一致率，分歧逐条看。
3. **和前两关缠在一起**。只看最终违反率，分不清是没找到还是没照做。
4. **容易被泄漏污染**。如果页面就是从被测会话本身学出来的，「有记忆」那一组等于提前看了答案（[第 03 篇](03-same-session-leakage.md)专门讲）。

**Next-step Replay 怎么测它**

- 从会话里切到纠正之前的最后一句用户话，后面的全部丢掉。公开版本用开源仓库上的合成会话。
- 对照组里有一组 `oracle_page`：把对的页直接放到 Agent 眼前。这一组把「找到」短路掉，剩下的违反就是纯粹的「用上」失败。
- 判官按规范的要点逐点打 `full` / `partial` / `violates`，两个独立判官，报三类标签上的一致率。
- 漏斗：搜了 → 搜到对的页 → 读了全文 → 照做。`memory_search` 组和 `oracle_page` 组的差距是「找到」的损失；`oracle_page` 组和满分的差距是「用上」的损失。
- 按页面来源（别的会话 / 同一会话 / 纠正之后才写的）分开报。

case 格式和对照组的定义见 [bench/next-step-replay](../bench/next-step-replay/README.md)。

## 夜间整理 ↔ dreaming

**它说了什么**

- **按原始记录核对纠错**。Pokémon 里有一条笔记把地标建筑记错了方向，Agent 据此判断「山洞已经走完」，结果反复掉回来路。dreaming 拿会话记录核对笔记、改对之后，Agent 回到山洞，走到了下一座城；没改的那一轮始终没过去。
- **wiki 会膨胀**。有一个任务里 wiki 长得比原始文档还大，像博尔赫斯《论科学的精确性》里和帝国一样大的地图，什么也没抽象。
- **多个 Agent 写同一页会丢事实**。几个 Agent 同时往一张共享的合同条款表里写，互相覆盖，57 个评分事实只留下 41 个（72%）；改成每份合同一个 Agent、一页、逐字引用条款之后，57 个全在。
- **整理指令要按目标定**。一开始的指令没说「合同条款是最重要的部分」；让 Claude 反思失败、改指令、重建 wiki，才发现这一点。
- 第二遍整理能补上指向不存在页面的链接。
- 开放问题：全量核对太贵，可能要聚焦在容易变的信息上，按访问频率定整理节奏。

**我们对得上的**

我们的夜间整理做四件事：合并近似页、改写、拆长页、挂关联链接。

- **把不相关的规范粗暴合并**。离线找近似簇再合并，两个判官逐组复核，**将近一半的合并有实质问题**：对象或适用范围不同的规范被混成一条，例外和条件被弱化。这些全部回滚，规范目录的合并现在默认先拦住。这和「多个 Agent 写一张表丢事实」不是同一个机制（我们不是并发写），但结果同类：把本该分开的东西压成一份，压的时候丢掉的正好是最值钱的细节。它丢的是合同条款原文，我们丢的是适用范围和例外。它的修法是一个对象一页、逐字引用；我们对应的硬约束是「合并不能丢引用」。
- **链接看着对，严查只有约六成对口**。夜间给规范挂上「规范 → 具体做法」的链接（指向经验页），上线时抽查几乎都过。换成严口径（判官读全文、要求检查冲突）全量复核，两个判官都认可的约六成，其余要么只是主题相关，要么和规范本身冲突。当初能过，是因为判官只看摘录、主题沾边就放行。这一条它没有直接对应，但和「wiki 和原文一样大」是同一个警告：表示层看着越来越丰富，不等于越来越有用。
- **门槛规则把该留的规范下线了**。一个按质量门槛自动下线规范的步骤，事后复核，**大部分被下线的规范应该恢复**，其余多是仓库说明文件里已经写过的重复。下线是看不见的失败：一条规范消失不会报错，只会在下次被纠正时才暴露。
- **一夜反复改写**。块里没变的邻页被顺手改写，约三成的页一夜被改两三次。已经修成「只写回有变化的页」。
- **核对原始记录**。我们的页每一句都带引用、能回到原始消息，所以「按原文核对」在机制上是可行的。但我们目前检查的只是「引用还在不在」，还没做「内容和原文对不对」。它的例子说明后一步值钱，这正是下面要做的实验。

它的「按目标定整理指令」放到我们这里，意思是：我们的整理指令是通用的（去重、改写、拆长页），从没说过「适用范围和例外是规范里最重要的部分」。按它的经验，这句话本该写进整理指令。【推断】

## 接下来做什么：在 Next-step Replay 上加「回看记录、核对记忆」

只是计划，还没跑。

**问题**：在 Agent 做决策之前，拿记忆页去对照它引用的原始记录，能不能减少「用上」这一关的部分照做，以及「写对」这一关的范围被写宽？

**对照组**

1. `memory_search`：现状，Agent 自己决定搜不搜。
2. `oracle_page`：对的页直接放在眼前。
3. `oracle_page + verify`：页旁边附上它引用的原始片段，要求 Agent 出方案前先核对页和原文是否一致，并把要点逐条列出来。
4. `dream_verify`：先离线跑一遍「按原始记录核对」的整理，把核对后的页放进检索，再跑 `memory_search`。

**数据**：开源仓库上的合成会话和纠正，先做 5–10 个 case。每个 case 故意埋几类有问题的页：范围被删掉的、和原文冲突的、已经过时的。

**指标**：逐点 `full` / `partial` / `violates`；两个判官的一致率；漏斗各层的比例；核对步骤多花的 token；核对把本来正确的页改坏的比例（误改率）。

**怎么读结果**：3 比 2 好，说明「用上」的损失里有一部分是没把页读成要点；4 比 1 好，说明整理时核对原文值得花这份算力；都没差别，也照实写。

**不做**：不在内部数据上跑这个实验再拿数字来发布；不做模型之间的比较。

## 小结

| 关 | Anthropic 的说法 | 我们的一线观察 | 对得上吗 |
|---|---|---|---|
| 写对 | 记忆是预测；说用途、不规定写法；固定规则会掉分 | 改 Skill 写法，49 道题差异在 1 题以内；适用范围比结论重要 | 方向一致，对象不同 |
| 找到 | 注入层要小；wiki + 搜索 61%，只搜索 53% | Agent 搜的是任务，规范讲的是步骤；排序不是瓶颈 | 互补：它给了地图，我们缺的是「知道这一步该查」 |
| 用上 | 一句话：加载了不保证照做 | 漏得最多的一关：读了全文却没完全照做接近四成；页摆在眼前仍约五分之一违反 | 它没展开，这是我们最想补的 |
| 整理 | 按原文核对；wiki 膨胀；多人写一页丢事实；按目标定指令 | 粗暴合并近半有问题；链接严查约六成对口；门槛误下线大部分该恢复 | 失败模式高度一致 |
