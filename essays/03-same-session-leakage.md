# 你的记忆评测可能虚高了：同会话泄漏

[English](03-same-session-leakage.en.md) · 中文

> 草稿 v0。文中「我们」的观察来自一个团队记忆系统的内部实践，只写粗粒度描述，不放原始数据和样例；样本小，场景是编程 Agent 的团队约定。例子都是改写或合成的。末尾的 Next-step Replay 结果来自公开合成案例的完整试跑，只是描述性结果，不是记忆有效的证据。

## 一句话

评测记忆时，如果「有记忆」那一组读到的页**来自被测会话本身**，或者是**纠正之后才写、才改的**，它就等于提前看了答案，收益会被明显高估。所以结果必须按页面来源（`page_origin`）分开报，只有来自别的会话、而且在纠正之前就已经存在的页，才能拿来说「记忆有用」。

## 我们是怎么踩到的

[第 01 篇](01-three-gates.md)里提过：从真实会话里取纠正之前那一步，分别在有记忆、无记忆时让 Agent 出方案，整体看有记忆时违反率下降很明显。逐个 case 看才发现，不少 case 用到的页**就是从这次会话学出来的**，有的是纠正之后才更新的。只看页来自别的会话、纠正后也没改过的干净 case，**收益几乎为零**。

这件事难发现，是因为每一步单独看都合理：

- 记忆系统每晚从所有会话里抽取纠正、写成页，这是它的本职。
- 评测集从日志里挑「被纠正过」的会话，这是最省事的出题办法。
- 重放时连上的是当前的记忆库，这是最省事的环境。

三件事放在一起，就是：拿一道题的答案去训练，再用同一道题考。机器学习里这叫**数据泄漏**（leakage），老问题。Kapoor 和 Narayanan 综述了 17 个领域里受泄漏影响的 329 篇论文，给出 8 类泄漏，有的结论因此「过分乐观」到复现不出来（[arXiv:2207.07048](https://arxiv.org/abs/2207.07048)）。LLM 评测里对应的说法是**测试集污染**：模型训练时见过测试集，分数就被高估（Sainz 等，[arXiv:2310.18018](https://arxiv.org/abs/2310.18018)）。记忆评测的泄漏是同一种病，只是「训练」换成了「写记忆」，而且发生得更快：不用等下一版模型，下一晚就漏进去了。

## 泄漏的几种样子

下面的例子都是合成的。设定：一个开源 Web 框架的仓库，团队约定「改了公共 API 要在 `CHANGELOG` 的 Unreleased 一节加一行，和代码一起提交」。会话里 Agent 改完接口准备提交，用户纠正：「changelog 呢？我们改公共接口都要写。」

**1. 同会话（`same_session`）**

夜间抽取跑过这个会话，把这句纠正写成了一页「改公共 API 要更新 CHANGELOG」。评测时把会话切到纠正之前重放，记忆库里正好有这一页，Agent 搜到、照做，判官判「照做」。

这一页的每句话都引用自被测会话。它证明的是「抽取器能把一句纠正写成页」，不是「别的会话学到的约定能在这里生效」。

**2. 纠正之后（`after_correction`）**

页本来是别的会话写的，但只写了「改公共 API 要通知下游」。被测会话的纠正发生后，整理步骤把「要写 CHANGELOG」并进了这一页。重放时读到的是并过之后的版本。

页的来源标签是「别的会话」，内容里却有被测会话的答案。只看页是谁创建的，标不出来；要看**每个版本是什么时候写的、每句话引用了什么**。

**3. 经过整理洗白**

比第 2 种更隐蔽：夜间整理把几页近似的页合并、改写，引用在合并时丢了（[第 02 篇](02-reading-the-components.md)里「合并不能丢引用」这条硬约束就是为此）。合并后的页查不到出处，看起来像一页老的通用规范，其实有一句来自被测会话。没有逐句溯源，这一类根本标不出来。

**4. 不在记忆里，而在题目里**

还有几种泄漏不经过记忆页，但效果一样：

- **prefix 切晚了**：切到了纠正那一句之后，或者最后一句用户话本身就带着提示（「先别提交，想想还漏了什么」）。第 02 篇说过，我们的评测集里有相当一部分题，被纠正的事和纠正前最后一句用户话说的不是一件事；切点不对，泄漏和错位都会出现。
- **仓库状态是事后的**：重放时检出的是修好之后的提交，`CHANGELOG` 里已经有了那一行，Agent 照着旁边的格式补上就行。这时连「无记忆」组也被抬高了，两组差距反而可能被低估，所以单看差距发现不了。
- **会话前面已经纠正过一次**：同一件事在会话早些时候已被纠正，答案就在 prefix 里。这测的是上下文内的记忆，不是跨会话记忆，应该单独标出来，不要算进记忆的收益。

**5. 挑题本身的偏差**

只挑「记忆库里有对应页」的纠正出题，等于只考第一关（写对）已经过了的题。这不是泄漏，但会让第二、三关的数字好看。至少要报一下：所有值得记的纠正里，有多大比例进了题库。

## 为什么常见基准和团队场景都容易踩

**事实召回基准：同会话就是题目本身**

[LoCoMo](https://arxiv.org/abs/2402.17753) 每段对话平均约 300 轮、9K token，最多跨 35 个 session，在上面考问答、事件摘要和多模态对话生成。[LongMemEval](https://arxiv.org/abs/2410.10813) 把 500 道题嵌进可伸缩的聊天历史里，考信息抽取、跨 session 推理、时间推理、知识更新和拒答五种能力。两者的设计都是：记忆从**这段历史**里建，题目问的也是**这段历史**里的事。

这不是缺陷，是它们要测的东西：「能不能从长历史里找回一个事实」。问题出在怎么读结果。[Mem0](https://arxiv.org/abs/2504.19413) 这类系统在 LoCoMo 上报的提升，对照的是 RAG 和全上下文这些「同一段历史的别的读法」；它说明的是在同一段历史里，记忆比别的读法更准或更省。如果把它读成「团队记忆能让 Agent 在另一个任务里少犯错」，就是拿一个 `same_session` 的数字当 `other_session` 的数字用。

两类场景的差别：

| | 事实召回基准 | 团队约定 |
|---|---|---|
| 记忆从哪来 | 被问的那段历史 | 别人、别的会话、往往很久以前 |
| 什么时候用 | 有人直接问 | 没人问，Agent 正要做某一步 |
| 答案在哪 | 历史里有（拒答题除外） | 只在记忆里；没记住就没有 |
| 同会话算不算泄漏 | 不算，是题目本身 | 算 |

LongMemEval 的「知识更新」一类和 `after_correction` 很像：新事实覆盖旧事实，考的是用新的那条。在事实召回里这是正当的考法；在纠正驱动的评测里，「纠正之后才更新的页」恰恰是答案本身。【推断】

**团队场景：泄漏是默认状态**

- **纠正就是记忆的原料**。抽取器最该写进记忆的就是纠正，而评测最想用的题也是纠正。所以越是高价值的题，越可能已经漏进记忆。
- **整理不停在改页**。合并、改写、拆页都会把新内容并进老页。只按「页是谁创建的」标来源，会把第 2、3 种泄漏全标成干净。
- **记忆库是共享的、一直在长**。评测通常连当前的库，而不是纠正那一刻的库。纠正那一刻和现在之间，别人可能也因为同一件事被纠正过，又写了一页。
- **省事的做法刚好全是漏的**。从日志挑题、连线上库、检出最新代码，每一步都在引入泄漏；要切干净，每一步都要多做一点。

## 在 case 设计上怎么切干净

**1. 切点：截在纠正之前**

- prefix 停在纠正之前的最后一句用户话，后面的全部丢掉，包括 Agent 之后的工具调用。
- 检查最后一句用户话和被纠正的事是不是同一件事、有没有带提示。对不上的题剔掉，不要硬留（第 02 篇的清洗就是这一步）。
- 如果同一件事在 prefix 里已经被纠正过，标成上下文内 case，单独报。

**2. 快照：一切都回到纠正那一刻**

- **仓库**：检出纠正发生时的那个提交，不是修好之后的。
- **记忆库**：只放纠正时间点之前就存在的页版本。理想做法是记忆库本身带版本，按时间回放；做不到，就至少给每页记下每个版本的写入时间，重放时把晚于纠正的版本挡掉。

**3. 给页打来源标签，按句子打，不按页打**

`page_origin` 取三个值，按下面的顺序判，命中一条就停：

1. 页里任何一句引用了被测会话的消息 → `same_session`。
2. 页的当前版本写于纠正之后（不管引用来自哪里）→ `after_correction`。
3. 其余 → `other_session`。

两条补充：

- **查不到出处的页不算干净**。引用丢了，就无法排除第 3 种泄漏，按 `after_correction` 处理。这是保守的做法，会少算一点收益，但不会多算。
- **按重放时实际读到的页打标签**，不只是 case 里预先列的页。`memory_search` 组里 Agent 自己搜，可能读到题目没列的页；一次重放的来源取它读过的所有页里最「脏」的那个。

这套标法依赖一个前提：**每句话都能回到原始消息**。这也是本仓库的 `memlite/`（还没写）把逐句溯源和带硬约束的整合列为必备的原因之一。没有逐句溯源的记忆系统，很难做干净的评测。

**4. 合成数据里故意造泄漏**

公开版本用开源仓库上的合成会话。干净的 `other_session` 页由另一个合成会话写出，措辞刻意和被测会话不同，避免判官和 Agent 靠字面对上。同时故意为一部分 case 造出 `same_session` 和 `after_correction` 版本，做成对照。同一道题在三种来源下的差距，就是泄漏能把收益抬高多少。

## Next-step Replay 打算怎么报

case 格式和对照组见 [bench/next-step-replay](../bench/next-step-replay/README.md)。报告上的约定：

- **主结论只用 `other_session`**。「有记忆是否减少违反」只看这一栏。
- **另外两栏单独列，永不合并**。`same_session` 和 `after_correction` 当作泄漏参照：它们比 `other_session` 好多少，就是混在一起时会虚高多少。
- **每一栏都写 n**。干净 case 往往最少，n 小就照实说「测不出差别」，不拿合并后的数字凑显著。
- **报来源分布**：题库里三种来源各占多少，以及查不到出处被按 `after_correction` 处理的有多少。
- **漏斗和判官一致率也按来源拆**。泄漏不只抬高最终违反率，也会抬高「搜到对的页」那一层：被测会话的原话和 Agent 此刻的 query 天然更像。【推断】

完整报告的格式示意（本次 demo 只覆盖其中部分组合）：

| 对照组 \ 页来源 | `other_session` | `same_session` | `after_correction` |
|---|---|---|---|
| `no_memory` | 违反率（n） | 违反率（n） | 违反率（n） |
| `memory_search` | … | … | … |
| `oracle_page` | … | … | … |
| `step_conditioned` | … | … | … |

`no_memory` 在三栏里理论上不受页的影响，如果三栏差得很多，说明这三组题本身难度不同，比较时要按题配对，而不是直接比栏。

## 评测 demo 结果

2026-11-15 的 [E002 Next-step Replay 完整试跑](../experiments/E002-next-step-replay-full/README.md)覆盖了 Click 上全部六个合成案例，只运行 `no_memory` 和 `oracle_page`。下面按 `page_origin` 分开报方案级比例，不合并来源，也不和早先的 [E001 冒烟测试](../experiments/E001-next-step-replay-smoke/README.md)合并。

每个标签的比例 = 该判官给出该标签的方案数 / 同一来源、同一组的全部方案数。`full` 是完全照做，`partial` 是部分遵守，`violates` 是违反；每格的 n 是被判方案数。一致率的分母是同一来源、同一组的成对判决数；三分类比较原标签，二分类只比较「是否违反」，都不是准确率。

| `page_origin` | 组 | 判官 A：full / partial / violates | 判官 B：full / partial / violates | 方案一致率：三分类 / 二分类 |
|---|---|---|---|---|
| `other_session` | `no_memory` | 50.0% / 25.0% / 25.0%（n=4） | 50.0% / 25.0% / 25.0%（n=4） | 100.0% / 100.0%（n=4） |
| `other_session` | `oracle_page` | 75.0% / 25.0% / 0.0%（n=4） | 100.0% / 0.0% / 0.0%（n=4） | 75.0% / 100.0%（n=4） |
| `same_session` | `no_memory` | 100.0% / 0.0% / 0.0%（n=2） | 100.0% / 0.0% / 0.0%（n=2） | 100.0% / 100.0%（n=2） |
| `same_session` | `oracle_page` | 100.0% / 0.0% / 0.0%（n=2） | 100.0% / 0.0% / 0.0%（n=2） | 100.0% / 100.0%（n=2） |

在 `other_session` 中，两位判官给出的违反率都从 `no_memory` 的 25.0% 变为 `oracle_page` 的 0.0%，但**不能说 oracle 方案一致被判为完全照做**。分歧在一个可选验证步骤：方案已明确使用 `terminal_width=48`，又建议换一个 `COLUMNS` 值验证。判官 A 认为这种环境改动在规则范围内仍有歧义，给 `partial`；判官 B 认为它只是检查独立性，不是测试的依赖，给 `full`。表中保留了两份原判，没有调解、改评分规则或选择性重跑。

**`same_session` 两组在两位判官下都是完全照做，但规则提醒早已在两组的 prefix 里。** 因而无记忆组也已经满分，不能把饱和表现当作记忆带来的新增收益。把这些控制题混进总分，会抬高判官 A 的「有记忆」完全照做率；判官 B 在 `other_session` 已满分，不会再升。这正是本文要求按来源分开报的原因，而不是跨会话记忆有效的证明。

**局限：只有六个手写合成案例、单一模型，只能作描述。** 规划器和两位判官都使用 `claude-haiku-5-5`；两次盲评的提示词不同，不等于不同模型，也没有独立的人类校准。试跑只评方案，没有执行补丁；提供完整页只能证明送达，不能证明读过，更未测检索或真实任务完成。`after_correction`、`memory_search` 和 `step_conditioned` 未运行。上述比例不是因果估计，**不是记忆有效的证据**。完整设置、原始标签和局限见 [E002 完整报告](../experiments/E002-next-step-replay-full/README.md)。

## 小结

| 问题 | 做法 |
|---|---|
| 页来自被测会话 | 按句子溯源，引用到被测会话就标 `same_session` |
| 页在纠正后改过 | 按版本时间判，晚于纠正标 `after_correction`；或回放到纠正那一刻的库 |
| 整理时丢了引用 | 查不到出处不算干净；整合不许丢引用 |
| prefix 或仓库状态带答案 | 截在纠正前最后一句用户话；检出纠正时的提交 |
| 结果怎么报 | 主结论只看 `other_session`；三栏分开、各写 n；不合并 |
