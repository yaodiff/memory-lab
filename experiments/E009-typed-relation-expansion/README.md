# E009 召回时沿实体关系扩一层：多页题一题没多找齐，扩不到主要是因为结果里没有可扩的实体

- 结论：Does not work
- 日期：开始 2026-11-20 / 结束 2026-11-20
- Issue / PR：#56 / 本 PR
- 来源：自己的想法（关系数据复核时发现召回链路不读关系类型）；数字均来自内部小样本，只报比例或粗略估计
- 交接：无

## 假设

团队记忆里有一类「实体页」（系统、服务、仓库、模块、概念），实体之间用固定词表写类型化关系，例如「属于／包含」「依赖／被依赖」「实现／被实现」。召回目前只按文字相似度，关系只作为每条结果末尾的「关联页」标题列表出现，Agent 读不读看它自己；排序里不用关系类型。

假设：搜到实体页时，沿这三组关系再扩一层，把邻居一起召回（追加或加分重排），能让一个编码任务要用的几页（所属系统、模块、相关经验）更容易一次找齐，同时不会明显把错页带进前 3。

判定线在跑之前写在 issue #56 里（下文「做法」摘录），权重也在运行前固定，没有调参。

## 做法

### 样本（规则先冻结，再生成，再跑）

- S1：冻结的检索评测集里，标注需要两页及以上的题（十来道）。
- S2：同一评测集里问「代码在哪」或标注页是实体页的单页题（十来道）。
- D：约 20 个真实编码任务，取自带完整工具回执的历史运行，按任务去重、每个空间最多 5 个。查询用 Agent 当时自己发出的第一次记忆搜索原句。金标 = 任务实际改动的仓库对应的实体页，加上「代码引用落在改动模块（仓库下前两级目录）里的系统类实体」；错页 = 代码引用全部落在未改动仓库的系统类实体。
- 多页题约 20 道（S1 加上 D 里金标 ≥2 页的任务），有错页定义的约 30 道，合计约 45 道，覆盖约 10 个空间。

### 检索与各组

每题对生产检索服务做一次只读请求（默认合并模式、最多 10 条、测试流量标记），并在请求前取同一批空间页面的只读快照，离线算各组。

| 组 | 做法 |
| --- | --- |
| A 现有召回 | 回执原样 |
| B 扩一层追加 | 种子 = A 前 5 中非弱相关的实体页；沿三组关系（双向，反向边自动补）取一跳邻居，排除失效页、个人页和已在列表中的页；按种子名次、关系优先级（属于 > 包含 > 实现 > 依赖）最多追加 5 条（列表 ≤15） |
| C 加分重排 | 邻居分 = 种子分 × 权重（属于 0.95、实现 0.90、包含 0.85、依赖 0.80）；已在列表、且是更靠前种子邻居的页每条关系 +0.03（上限 +0.06）；排序后截 10 |
| 诊断 U | 无类型一跳（任意链接或反链、任意页型），追加 ≤5 |
| 诊断 B+／C+ | 先按代码引用给没有上级的实体补「属于 仓库实体」，再跑 B／C，用来估计「关系补全后」能好多少 |

固定参数见 [`config.json`](config.json)。

### 指标与归因

- 多页全中率（多页题；B、U 看全列表，其余看前 10）、任一金标进前 3／前 10、错页进前 3、空结果、额外开销。
- A 前 10 没命中的每个金标页归入：扩展够到／金标不是实体（按设计扩不到）／没有种子／有种子但无联系／关系缺失（有共同代码仓库或无类型链接，但没有三组类型边）。

### 判定线（运行前登记）

- **Works**：B 或 C 多页全中至少多 3 道且至少 +15 个百分点；前 3 命中最多少 1 道；错页进前 3 最多多 1 道；无新增空结果；每题最多一次额外查页。
- **Does not work**：B、C 多页全中都最多多 1 道，且扩展没够到的实体金标页里「关系缺失」不到一半；或增益 ≥3 道的组同时多出 ≥3 道错页进前 3。
- **Inconclusive**：其余情况，包括「关系缺失」占一半及以上（方法在现有数据上无法判断）。

## 数据

所有检索请求都成功返回，无降级，无空结果；回执中的记忆条目全部能对上快照里的页面。

### 三组对比（内部小样本，约 45 道题）

| 指标 | A 现有 | B 追加 | C 重排 | 诊断 U | 诊断 C+ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 多页全中率（约 20 道多页题） | 约 44% | 约 44% | 约 44% | 约 44% | 约 44% |
| 任一金标进前 3 | 约 45% | 约 45% | 约 43% | 约 45% | 约 43% |
| 任一金标进前 10 | 约 55% | 约 55% | 约 59% | 约 55% | 约 59% |
| 任一金标进全列表（B、U 最长 15） | 约 55% | 约 61% | 约 59% | 约 59% | 约 59% |
| 错页进前 3（约 30 道有错页定义的题） | 约 6% | 约 6% | 约 13% | 约 6% | 约 13% |
| 扩展页挤进前 3 且不是金标 | 0 | 0 | 约 9% | 0 | 约 9% |
| 空结果 | 0 | 0 | 0 | 0 | 0 |
| 平均返回条数 | 约 10 | 约 11 | 约 10 | 约 12 | 约 10 |

- **多页全中率三组一题未变。** B、C 都没有多找齐任何一道多页题。
- 只有在真实编码任务的「找到改动仓库的实体页」上有一点变化：仓库页进入结果的比例从约 5% 升到约 20%（B），但多出来的都排在第 11–15 位，前 10 不变；C 把它们中的一部分插进前 10（约 15%）。
- C 多出的错页进前 3 都是扩展页本身：种子实体「属于」一个本任务没有改动的仓库，或一组概念实体「属于」另一个服务，重排把这个上级抬进了前 3。
- C 前 3 少命中的那一题与关系无关：生产的最终顺序经过按页型的混排，并不是纯按分数排（约 86% 的题如此），C 按分数整体重排后，分数略高的页越过了对口页。不加任何邻居、只按分数重排也会丢这一题（事后检查）。
- 诊断 C+（按代码引用补「属于」边后再跑）与 C 完全相同。补上的边大多落在没有被召回的实体上，而被召回的种子多是需求、项目、概念类实体，没有代码引用，补不到。

### 没扩到的金标页归因

A 前 10 没命中的金标页里，扩展够到的约一成，金标本身不是实体页（决策、经验）的约一成，后者按设计扩不到。其余扩展没够到的实体金标页：

| 原因 | 占比 |
| --- | ---: |
| 没有种子：A 前 5 里没有非弱相关的实体页，方法不触发 | 约 48% |
| 有种子但无联系：种子与金标页没有共同代码仓库、也没有任何链接 | 约 36% |
| 关系缺失：有共同仓库或无类型链接，但没有三组类型边 | 约 16% |

- 按登记口径，关系缺失约 16%，不到一半。
- 事后人工看「有种子但无联系」的页（未登记，只作上限）：约一半其实是「该连没连」，例如业务实体应被某个服务「实现」却没有边、正文也没提这个服务，或者组件实体没有挂到它所在的仓库；另一半是查询本身跑题（问的是文档工具怎么用）。把前者也算作关系缺失，上限约 36%，仍不到一半。
- 只有约一半的题在 A 前 5 里有可扩的实体；真实编码任务里，仓库实体页直接进前 10 的约 5%。仓库实体页在关系图里也很稀：关系行数中位数约 2，很多落在该仓库里的需求和组件实体并没有连到它。

### 开销

- 离线扩展计算每题不到 0.03 毫秒；每题邻居数中位数 0，最多个位数。
- 关系类型可以从召回链路已经取回的命中页正文里直接解析，不增加查询；把邻居作为结果返回需要一次按页 ID 的批量查询（推断为毫秒级，没有在线测）。

## 结论

- 结论：**Does not work**。B、C 的多页全中率都没有提高（增益 0 道，登记线要求至少 3 道），扩展没够到的实体金标页里关系缺失约 16%（事后放宽口径上限约 36%），都低于一半，命中「Does not work」的第一条。C 还多出了错页进前 3。
- 不是「关系数据不全，所以方法没机会」：最大的一块是召回结果里根本没有可扩的实体（约一半），其次是被召回的实体（需求、项目、概念）和要找的仓库之间本来就没有联系。这两块在补关系之前就已经卡住了，补边的诊断组也确实没有改善。
- 值得保留的证据：
  1. 编码任务的「找到改哪个仓库」主要卡在召回阶段——仓库实体页很少被查询原句召回，前 10 只有约 5%。
  2. 「属于」边挂错或口径不一时（项目实体挂到它没改的仓库），按关系加分会直接把错页抬进前 3。关系做排序信号之前，先要有关系质量的检查。
  3. 生产结果的最终顺序含有按页型混排等后处理；任何「加分重排」实验都要在生产最终顺序上插入，不能用原始分数整体重排，否则会把后处理的效果误算到新方法头上。
- 对相关实验的影响：#26（类型化关系能否减少纠正）在召回侧没有得到支撑；若要继续，优先改写入侧（给有代码位置的实体补上级仓库、让需求实体连到实现它的仓库），而不是在召回侧沿关系翻页。

## 没覆盖的

- 样本小：多页题约 20 道、真实编码任务约 20 个、约 10 个空间，单题变化就是约 5 个百分点。只代表我们自己的设置。
- 编码任务的金标是机械规则（同名仓库实体 + 改动模块内有代码引用的系统实体），没有人工复核；同名匹配没算别名。
- 编码任务的查询是 Agent 当时自己发的第一次搜索，有几题偏离任务本身，这类题任何召回改动都救不了。
- 页面快照与检索相隔几十分钟以内，期间页面可能有变化；按页 ID 全部对上，未发现失效页。
- 只测了一跳；没测两跳、没测「实体 → 挂在它下面的经验/决策页」这类按类型的扩展（只在无类型诊断里粗测，同样没有多找齐多页题）。
- 额外的在线延迟没有实测，只有离线计算耗时和查询次数推断。
- 没有跑 Agent 端到端（是否因此少走弯路、少读错页），也没有外部基准。

## 后续发现（2026-11-20）

- **Does not work**。内部生产候选的只读回放确认：一跳追加和按关系加分都未提高多页全中率（约 44%）。加分组有错页进前三的比例约从 6% 到 13%。复盘应先查首轮有无可扩的实体，以及种子是否与任务对象有关。按代码引用补边的诊断组复算后分数相同。
- **Inconclusive**。先用任务语境找到仓库或服务，再验证关系召回，属于待测的另一条路径。这里的证据来自生产候选和离线扩展，线上扩展开销及长期纠正率未测。存量页该挂到哪个实体的离线复核见[记忆整理](../../lessons/memory-curation.md)，查询时机与措辞见[检索复盘](../../lessons/memory-retrieval-traces.md)。
