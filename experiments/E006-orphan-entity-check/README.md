# E006 孤立实体判定：小模型只看页首、不对代码、不二审，以及「正文带代码引用」当候选过滤器

- 结论：Does not work
- 日期：2026-11-20 / 2026-11-20
- Issue / PR：#37 / #44
- 来源：自己的想法（对一次内部质量盘点结论做代码对照复核）
- 交接：无

## 假设

本实验里「孤立实体」的口径是：团队记忆里的实体页，既没有「属于」上级，也没有子实体。它只是导图的展示桶，不等于「应该是顶层」。问题有两个：

1. 一个小模型只读每页正文的前几行、不看代码、结果也不经二审，能否可靠判出「这页本来就该是顶层或独立实体、不需要上级」？
2. 「正文带代码引用」能否当候选过滤器，用来圈出「最可能该补上级」的那批孤立页？

判定线为事后整理，未事前登记。事后采用的线是：

- 问题 1：对照代码复核后，第一轮「不需要上级」的判定若有相当比例（明显高于个位数百分比）被推翻，记 **Does not work**。
- 问题 2：圈出来的候选，经代码核对后能确认挂上级的比例若不明显高于不加过滤的随机抽样，记 **Does not work**。
- 两个问题都成立才记 **Works**；一成一败或样本撑不住，记 **Inconclusive**。

## 做法

数据来自一个内部知识空间群，规模为约六千个被第一轮判为「不需要上级」的实体页，称为 root 桶。以下均为内部小样本，只报比例。

**第一轮（被复核的方法）**

- 模型：一个小模型，推理强度低，批量判定。
- 输入：每页正文前 10 行（每行截断），加最多 7 个同空间候选页（按标题分词召回）。不提供代码，不提供空间声明的仓库清单，也不提供目录结构。
- 分桶举证不对称：判 root 只需「正文支持它是独立系统、总览、产品或横向概念」；判「缺上级」则要求「正文明确指出它是某个具体上级的组成部分」，且不许凭命名推测。
- 二审：只对「建议挂上某个候选」的那一小批做了换模型复核，root 桶没有任何二审，只作建议、未写线上。

**对照代码复核**

- 从 root 桶按固定随机种子抽 36 条，另看了上一轮报告点名的 4 个例子。
- 每条对照业务代码、空间声明的仓库清单、仓内文档和同空间已有实体。复核由 3 个子 Agent 按同一份判定说明分批做，主 Agent 抽查了其中少数几条的证据。判官全是模型，**这不是人工抽查**。
- 判定分四类：A 应挂上级且上级页已存在；B 应挂上级但上级缺页；C 不应有「属于」（真顶层，或外部平台、通用技术、第三方库、他空间服务这类「属于」本来就不适用）；D 证据不足（多因读不到代码仓）。
- 对 root 桶做全量机械统计：子类型分布、正文是否带代码引用。

**用「正文带代码引用」圈候选，再修**

- 复核报告提议，第一批先处理「正文带代码引用、且所在仓库的实体页已存在」的 root，认为这是置信度最高的候选。按同空间、非个人页、非自指和标题归一化重建这批，复现了三百多条（报告原计数与重建数之间约差一成，未能一一对应）。
- 对重建出的每一条逐条对照代码重审。只有「挂已有业务系统页」或「仓内组成部分挂最近的现有实体」且有源码锚点的才算合格。通用、外部、共享仓、开发环境类上级一律排除，读不到仓记证据不足。
- 另在「正文带代码引用」的另一池里补足试点，凑到约 20 条，先写生产、逐条读回，再让独立复核对着源码核验；约定试点正确率须不低于 90%。
- 修之前先备份，写后逐条读回，并用一组固定的 14 题正例回放，确认前 3 与前 10 命中不退化。

## 数据

### 第一轮的结论被推翻了一部分

36 条随机样本，对照代码后：

| 复核判定 | 占比 |
| --- | --- |
| A 应挂上级，且上级页已存在 | 约 25% |
| D 证据不足（多数倾向有上级） | 约 11% |
| C 不应有「属于」 | 约 64% |
| B 应挂上级但上级缺页 | 0 |

- 第一轮「该是顶层或独立」被推翻的比例：确定被推翻的约 25%，把证据不足也算上界约 36%。外推到整个 root 桶，应挂上级的主估计约四分之一（Wilson 95% 区间约 14%–41%，样本小、区间宽）。
- 64% 的 C 里，约七成是外部平台、通用技术概念、第三方库或他空间服务，「属于」不适用，留在独立桶是正确的。所以结论对的那部分，理由多数写错了：应写「用依赖/实现/是一种，不用属于」，而不是「候选只是调用关系」。
- 判错（应挂上级）的那几条里，约三分之二在代码里一眼就能看到所属仓库或模块（例如一个仓内目录里的封装、一个仓里的具体组件），第一轮没给代码，自然看不到。
- 同一轮内标准不一：同样是空间声明的仓库、同样有工作区页的两个服务，一个被判成了聚合项目的组成，另一个被判成 root。
- 页面与代码不一致的事实也在复核中冒出来，样本里约十分之一的页混写了两个仓或已过期，第一轮不对代码，当然发现不了。

### 第一轮错在哪（方法层面，来自提示词与调用方式的核对）

- 把「候选里没有上级」「正文没点名上级」当成了「不该有上级」。提示词里本来写了「没有候选不等于顶层」，但模型给出的 root 理由大量就是「候选只是调用关系」「正文未写明隶属」。
- 判 root 的举证门槛低于判「缺上级」，一个服务页只要写「X 是一个服务」就够判 root，而它所在仓库或系统几乎从不被正文点名。
- （推断）页首几行加几个标题召回的候选，信息里没有「它在哪个仓、哪个目录」，而这恰恰是「有没有上级」的决定因素。
- root 桶没有二审，所有错误直接以「建议」形式进了台账。

### 「正文带代码引用」当候选过滤器

- 召回很低：root 桶里正文带代码引用的不到一成（约 9%），其余九成多没有引用。在 36 条随机样本里，复核判 A 的页没有一条正文带代码引用；带代码引用的两条都判 C。
- 精度也很低：把「带代码引用且所在仓库实体已存在」这一批最高置信候选重建出来逐条重审，经代码核对合格的只有约 3%。其余多数是调用方、外部或通用概念、共享仓、仅引用生成模型之类。典型情形是页面正文引用了某个仓的代码，但该仓只是调用方或使用方，并不拥有该概念。
- 这个 3% 低于对整个 root 桶随机抽样得到的约 25%，但两者口径不同：重审时的合格线更严（必须有现成业务系统页作上级、必须有源码锚点），而随机抽样把「依赖口径」的 A 也算进去了。所以只能说：代码引用既不能保证召回，也看不出对精度有帮助，不能当过滤器。「代码引用」只能当核对线索，不能当判据。
- 重审中因读不到仓、无源码而判证据不足的只占约一成，多数跳过是有源码证据否定了归属，所以 3% 不主要由读不到仓造成。

### 按代码重判后的做法与结果

- 规则：先按代码确定实体「是什么」，再选关系。仓内的目录、模块、子应用、组件、封装必有上级；外部平台、通用技术、第三方库、他空间系统、共享仓不用「属于」，改用依赖、实现、是一种；读不到仓记证据不足，不记 root；判 C 须说明属于哪一类。
- 约 20 条试点经独立代码核验，正确率 90%，刚好压在约定线上。两条选错：它们都把业务概念挂给了相邻一层的适配或打包服务，实际的业务所有者是另一个服务。这类错误只看「页面引用了哪个仓的代码」判不出来，要看哪个仓实际持有业务逻辑。
- 两条错误按备份回滚并读回，之后依据复核给出的源码改挂到正确上级，最终保留的约 20 条在生产上逐条读回通过，原正文逐字保留。
- 全库孤立实体占活跃实体的比例从约 48.4% 变成约 48.3%，几乎没动。写入只涉及约 20 页，只改了很小的一部分；这次不是要降孤立率，而是确认这套做法能写对。同一时间窗口里别的页也在进出孤立集合，这点读数差异不能归因于本次写入。
- 14 题正例回放：前 3、前 10 命中在写前、试点后、回滚后、纠正后四个时点完全一致，没有退化。
- 因重审合格率只有约 3%，没有放量，其余候选都留了逐条跳过原因。

## 结论

- 问题 1：**Does not work**。小模型只看页首、不对代码、不二审，判「不需要上级」不可靠。对照代码后，约四分之一被确定推翻，上界约三分之一多；结论对的那部分理由也写错。root 桶没有二审，是这些错误能进台账的原因。
- 问题 2：**Does not work**。「正文带代码引用」既只覆盖不到一成的 root 页，圈出的候选重审合格率也只有约 3%，不能当过滤器。
- 综合记 **Does not work**。
- 值得保留的经验：
  1. 「候选里没有上级」不能推出「不该有上级」；有没有上级由实体在代码里是什么决定，不由正文有没有点名决定。
  2. 判「不需要」与判「需要」的举证门槛要对称，否则「不需要」会成为默认出口。
  3. 判定孤立要带代码或仓库声明；读不到代码时判证据不足，不要当作顶层。
  4. 代码引用只是核对线索，不是候选过滤器；「挂在哪一层」要看谁实际持有业务逻辑，仅看谁引用了代码会选错层（试点里错的两条就是这样）。
  5. 判「孤立」的统计口径要先扣掉「属于」本来就不适用的实体（外部、通用、共享仓），否则孤立率会把它们当缺陷。
  6. 批量判定要有二审，root 这类「不动」的结论也要抽检。
- 对其他实验或文章的影响：无直接冲突；与 [记忆整理教训](../../lessons/memory-curation.md) 中「合并与标准」一节的「按主题整合，让整理模型可以核对代码」一致。

## 没覆盖的

- 随机样本只有 36 条，区间很宽；只复核了 root 桶，其余几个桶没复核。
- 部分样本因读不到代码仓判了证据不足，相关结论带推断；复核者全是模型，没有人工复核，主 Agent 只抽查了少数几条。
- 正文用的是第一轮冻结的快照，不是线上最新版本。
- 「同名实体」只做了标题精确匹配、未算别名；仓库缺页比例可能偏高估。
- 3% 的重审合格率来自一次重建的候选集，与报告原计数约差一成，没能一一对应；其口径比随机抽样严，二者不能直接相减当作「过滤器的提升」。
- 补足试点的那一池，只用来凑足约 20 条，没有给出该池本身的合格率。
- 「仓库是否挂到空间或业务系统聚合页」的口径没有最终拍板，多个判定取决于它。
- 没有做「小模型 + 代码」或「较强模型只看页首」的对照，因此不能区分是「模型小」还是「不对代码」造成的错误；本实验只证明缺代码这一路径不行。
- 只做了离线复核和一次小规模写入，没有长期观察是否有回退。
