# E007 去掉文档召回腿：延迟大幅下降、正确页未丢，但错页改善有限

- 结论：Inconclusive
- 日期：开始 2026-11-20 / 结束 2026-11-20
- Issue / PR：#35 / 本 PR
- 来源：内部上线前后对照（小样本，数字均来自内部小样本，只报比例或粗略估计）
- 交接：无

## 假设

团队记忆检索的默认模式会把两路结果合并：一路是记忆页（团队沉淀的页面），一路是独立的文档检索腿（直接检索文档库）。假设：

1. 去掉文档腿，错页进前 3 的情况会减少。
2. 对口的记忆页不会因此丢失。
3. 文档腿是慢路径，去掉后请求延迟明显下降。

判定线：**没有事前登记。** 本记录是上线决定做出之后整理的，不是先写线再跑。事后只按上面三个问题回读，不据此补设阈值。因此结论不会落在 Works。

## 做法

- 数据一（离线重算）：一个 48 题、覆盖 6 个空间的冻结检索评测集，每题取一份生产检索回执（合并模式，每题最多 10 条候选）。其中 45 题标注了对口页，34 题标注了已知错页，3 题是不应召回任何页的负例。评测集里的对口页标注几乎都落在记忆页上。做法是从既有回执里删掉文档候选，按原顺序紧缩名次，再按冻结标签重新计分。
- 数据二（错位坏例回放）：9 条已登记的召回错位坏例，对应 17 个原句，每个原句在同一配置下跑 2 轮，保留原有的结果条数上限与类型过滤。
- 数据三（上线后复跑）：下线发布后，对同一个 48 题集做一次只读复跑，另用 MCP、CLI 两个客户端各发 20 次请求（17 个坏例原句加 3 条正例）。
- 对比两端：下线前（合并模式的原回执）与下线后（文档腿关闭）。下线由服务端的运行时配置开关控制，默认关闭文档腿，把开关设回即可恢复旧行为。
- 数据集不公开：含内部页面与原句，本仓库只放聚合结论。

## 数据

### 离线重算与上线后复跑（48 题）

| 指标 | 下线前 | 下线后 |
| --- | ---: | ---: |
| 对口页进前 1（45 题） | 约 69% | 约 69% |
| 对口页进前 3（45 题） | 约 82% | 约 84% |
| 对口页进前 10（45 题） | 约 91% | 约 91% |
| 标注错页进前 3（34 题） | 约 6% | 约 6% |
| 空结果（48 题） | 0 | 0 |
| 前 3 含文档候选的题 | 约 27% | 0 |

- 离线重算与下线发布后的生产复跑，在对口页前 1 / 前 3 / 前 10 上完全一致，前 3 多命中的只有 1 题。复跑和下线前相隔数小时，期间服务端版本和部分页面内容可能有变化，但逐页核对后，在已改动的页里没有找到与评测标签相交的页。
- 约 56% 的题原本带有文档候选，其中约 27% 的题在前 3 里有；下线后全部归零。
- 严格匹配下，没有一道已命中的对口页因下线变成未命中。前 10 仍未命中的 4 题，下线前后都未命中，其中有 2 题的同标题记忆页排第 1（严格匹配缺页 ID，只在宽口径诊断里可见）。
- 宽口径（同标题）诊断里，错页进前 3 的题数下线后变化不到 1 题：离线重算多 1 题（记忆页上移到第 3），生产复跑少 1 题。两者互相抵消，看不出方向。
- 去掉文档候选会让后面的记忆页名次前移，同样可能把错的记忆页抬进前 3。这在评测集中至少出现过 1 题（错页从第 5 升到第 3）。

### 错位坏例回放（9 条、17 个原句，两轮）

| 指标 | 下线前 | 下线后 |
| --- | ---: | ---: |
| 至少一个已标错页进前 3 的案例（9 条） | 全部 | 约 89%（一条消失） |
| 至少一个已标错页进前 3 的原句（17 个，两轮） | 约 88% | 约 82% / 约 71% |
| 前 3 内已标错页的条次（两轮） | 基准 | 约 −14% / 约 −27% |
| 对口页进前 3 的案例（有标签的） | 全部保留 | 全部保留 |
| 严格达标（对口页进前 3 且错页全出前 3，9 条） | 0 | 约 11%（1 条） |
| 空结果的原句 | 约 6%～12% | 同左 |

- 错页减少是真实存在的，但幅度很小：多数坏例的错页本身就是记忆页，下线文档腿拿不掉它们。
- 上线后复跑（MCP / CLI 各 20 次请求）：全部请求成功，文档候选为 0，3 条正例的对口页都保持第 1。17 个坏例原句里仍约七到八成有错页进前 3，与离线回放的水平一致。

### 延迟

| 指标 | 下线前 | 下线后 |
| --- | ---: | ---: |
| 延迟中位数 | 约 2.2 秒 | 约 0.6 秒（约 −72%） |
| P95 | 约 3.2 秒 | 约 1.7 秒 |
| 最大值 | 约 4.1 秒 | 约 2.1 秒 |
| 文档腿超时或不可用的请求 | 约 15% | 0 |

- 约九成的题延迟下降；不到一成的题延迟持平或略升，下线前它们都已在约 1.3 秒以内。
- 下线前约 15% 的请求里文档腿超时或不可用，下线后这类降级消失。推断：合并结果要等这条腿返回或超时，所以它主要拉高尾部延迟；超时请求对中位数的影响没有单独量过。

### 失去了什么

- 文档腿提供的是实现参考、规范文档一类的第二路佐证。回放里至少有两个坏例原句，文档候选原来排第 1，对口的记忆页排第 2；下线后记忆页升到第 1，答案在记忆页里仍然完整，只是失去一份实现侧参考。
- 有一个坏例，记忆页修复后原本可以和一份文档互为佐证；下线会失去这条将来的第二来源。
- 有一道直接问旧版双路搜索契约的评测题，对口的两页（设计页与回源规范页）下线前后都没有命中；它丢掉的是文档腿里的阅读指南类候选，存档没有证据说明这些候选能单独答出那个问题。
- 在 48 题与 9 条坏例的存档范围内，没有找到一题因下线而失去唯一能答出问题的来源。这只覆盖了「已返回的候选」，不等于文档腿没有独占价值。

## 结论

- 结论：Inconclusive
- 延迟：下降是明确的（中位数约 −72%，降级请求归零），方向与假设 3 一致。但对比的是两个不同时段的运行，服务端版本也不同，不是同一时刻的对照实验，幅度不能全部归功于下线。
- 对口页：在已覆盖的样本里没有退化，前 3 反而略有提高，与假设 2 一致。
- 错页：评测集上没有变化，坏例回放里有小幅减少，宽口径诊断方向不一。假设 1 只得到弱支持，不能说「错页减少」是下线的稳定收益。
- 判定线是事后整理的，没有事前登记，且正确页的标注几乎全部落在记忆页上，天然看不到文档腿的价值。上述两点让「Works」站不住，没有出现足以判「Does not work」的退化，所以只能判 Inconclusive。
- 值得保留的经验：①「去掉一路候选」会让剩下的候选名次前移，可能把别的错页抬进前 3，评估时要同时看错页的增减；② 延迟收益推测主要来自慢路径本身及其超时与降级，不是排序质量（未做拆分验证）；③ 先下线、留恢复开关的做法适合这种「证据没有明确反对」的决定，但仍要用没覆盖的空间补验证。

## 没覆盖的

- 判定线事后整理，没有事前登记。
- 数据全部来自内部小样本：每个空间的题量从个位数到十余道，评测集以主项目空间为主。结果不应外推到别的团队或别的检索系统。
- 评测标注以记忆页为主，文档腿独占的价值（答案只出现在文档里的问题）没有被测到；记忆页稀疏、原来靠文档腿补满结果的空间覆盖不足。
- 没有任务级得分、采纳率、用户反馈，只看了「已返回候选」的名次。下线后别的候选补位带来的下游影响无法从存档里量出。
- 延迟对比不是同时同条件的 A/B：两个时段负载不同，服务端版本不同，也没有重复运行估计波动。
- 每题只做了一次检索（坏例做两轮），没有评估重复检索的稳定性。
- 没有测试「文档腿下线」与 [E003](../E003-llm-rerank-vs-hard-drop/README.md) 里的两段式重排叠加后的表现。后者只作用于记忆页一路，原本就没覆盖到文档候选。
- 坏例集合同时也是内容修复的依据，样本很小（9 条），错页减少幅度不宜直接引用。
