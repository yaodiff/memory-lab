# Plan：团队记忆质量治理（写对、搜得到、用得上）

- 状态：草案
- 日期：创建 2026-11-19 / 最后更新 2026-11-19
- 总 issue：#17 / 拆出的实验：见下方各 milestone 的 issue（相关：E003 / #16）

## 背景与问题

团队记忆要帮到编码 Agent，要过三道关：[写对、搜得到、用得上](../essays/01-three-gates.md)。我们在一个内部场景里用大约两周集中治理了这三道关。这份 plan 只写通用做法、取舍和步骤状态，结论是粗粒度的，来自小样本，不代表通用结论。

总体状态：

| 关 | 状态 |
| --- | --- |
| 写对 | 改善明显，主要来自写入规则和写后检查 |
| 搜得到 | 改善很小。多数想法没有越过事先定好的门槛 |
| 用得上 | 搜到之后基本会照做，但「搜到」本身是瓶颈，这一关几乎没有单独改善 |
| 少被纠正 | 尚未证实，要等足够长的观察窗口 |

另一个发现：我们自己的评测设置多次高估或掩盖了效果。这些失败方式单独记在 [评测教训](../lessons/memory-eval.md)，写入与整理方面的在 [整理教训](../lessons/memory-curation.md)。

## 目标 / 不做什么

目标：

- 让 Agent 在真实开发中少被纠正，而不是让记忆条数更多。
- 把「哪些做法有效、哪些无效、为什么」写成别人可以复用的取舍。

不做什么：

- 不在 Lab 里放内部系统的名字、数字、样例和链接。内部明细留在内部文档。
- 不把内部小样本结论包装成通用结论。需要数字的结论，用合成或公开数据在实验 issue 里复现。
- 不在这份 plan 里决定产品改动。需要交接时，走 `handoff/` 的公开交接卡。

## 方案

组织方式：Plan（本文）、Milestone、Issue、Task 四层。

- **Milestone**：对应 GitHub 上的 milestone，写目标、退出条件、状态。
- **Issue**：一个具体问题或假设，写结论（行 / 不行 / 说不清）。尚未做完或待验证的有真实 GitHub issue，链接写在标题里。已经做完的历史尝试不开 issue，只留在 task 里（标「无 issue」）。
- **Task**：issue 下的一次尝试，只写通用做法、结果、失败或放弃的原因。失败的尝试保留。

结论里的「行 / 不行」来自内部小样本，只代表那个场景；「说不清」表示样本太小、判官意见不一或效果混杂。

## 步骤

### [M1 写入质量](https://github.com/yaodiff/memory-lab/milestone/1)

- 目标：新写入和存量的页达到事先写好的质量标准，靠写入时的检查保证，不只靠提示词。
- 退出条件：结构类缺陷在写入前被拦截；批量改写有演练过的回滚；纠正泛化的假设有结论。
- 状态：内部大部分达成，剩余是在公开或合成数据上的验证。

#### Issue：写入要有证据与准入（无 issue，已完成）

- 结论：行（内部小样本）。
- [x] Task：规则和决策要求用户原话或可核对的代码作依据，只有模型推测的条目只当线索。结果：行。
- [x] Task：评测与采集会话不进记忆。结果：行，直接修复了答案泄漏。
- [x] Task：整体重写提示词让模型一次写对。结果：不行，只是「少写」，值得留的比例几乎不变，还丢有用条目。放弃，改为只定点改规则，精度靠写入后的整理。
- [x] Task：状态节只写决策状态，不写进度；经验页不写当次结果。结果：行。
- [x] Task：写完后单独做一次性细节检查。结果：行。把同样的规则直接塞进主提示词：不行，条目变少但缺陷占比几乎不变。

#### Issue：把一次纠正自动变成规则（[#19](https://github.com/yaodiff/memory-lab/issues/19)）

- 假设：多数纠正只对当次有效，单次纠正泛化不可靠。结论：说不清（内部倾向不行，待合成复现）。
- [x] Task：纠正后自动提炼规则并写回。结果：不行。写回前的 grounded 检查多轮都没同时达到「放行里坏的少、好的保留多」，样本外大多数不该写。放弃。
- [x] Task：冲突页自动加「用户纠正过」标注。结果：不行。原因：只看纠正那一句，没看用户几分钟后的改口。默认关闭。
- [x] Task：写回前检查用户后来有没有改口，并要求摘出改口原话。结果：行（初版拦得过宽，收紧后可用）。
- [x] Task：改成只判不写，把「该学没学」清单当检索考题。结果：行。
- [ ] Task：#19 在合成纠正流上比较「首次纠正就写」与「重复或明确要求才写」。

#### Issue：批量改写与回滚（[#20](https://github.com/yaodiff/memory-lab/issues/20)）

- 问题：批量改存量页的安全性取决于抽检和回滚。结论：说不清（做法有效，回滚没有系统演练）。
- [x] Task：让模型整批重写存量页，同时要求不升级、不降级、不删名字。结果：不行。错误率波动大，还悄悄删结构。放弃，改成加提示或程序化补丁。
- [x] Task：先抽检小批、设错误率门槛、过线再放量，写入前备份。结果：行。
- [x] Task：结构（章节、引用、标题形态）由程序校验。结果：行。
- [x] Task：门槛判定与写线上分属两条指令。结果：不行。已经写了才收到「未过线」。改为写进同一条任务，未过线默认不写。
- [ ] Task：#20 写一份回滚演练清单，在合成例子上演练一次。

### [M2 让 Agent 搜得到](https://github.com/yaodiff/memory-lab/milestone/2)

- 目标：Agent 在做决定的时刻去搜，并且搜到对的页。
- 退出条件：在真 Agent 上越过事先写好的命中率门槛，且触发率、命中率分开报告。
- 状态：未达成。想法很多，越过门槛的很少。

#### Issue：触发率与命中率是两个独立瓶颈吗（[#21](https://github.com/yaodiff/memory-lab/issues/21)）

- 假设：「该搜时不搜」和「搜了也搜不到」是两个瓶颈，把触发时机写在必读位置只解决前者。结论：说不清。
- [x] Task：在工具说明里加「做决定前再搜一次」。结果：受控对照有效，真实会话没有定论（样本小）。
- [x] Task：把「交付前按动作逐个搜」写进 Skill 正文。结果：不行。原因：大量运行根本没打开那个文件。
- [x] Task：把同样的要求写进一定会读的位置（描述字段、项目入口文件）。结果：找到率有提升；违反率两个判官方向相反。说不清。上线时明确标注了严格门槛未过。
- [x] Task：加一个「这一步在做什么」的可选搜索参数；只改参数说明。结果：不行，真 Agent 几乎不填或仍搜业务词。
- [x] Task：把搜索写法改成中途检索、精简结果。结果：说不清，对照几乎无差别。
- [x] Task：把 Skill 瘦身、压缩后不重搜。结果：行，减少了重复搜索造成的拖慢。
- [ ] Task：#21 在公开任务上独立操纵指令位置与检索质量。

#### Issue：目录、索引、归类让 Agent 自己翻（无 issue，已完成）

- 结论：不行（规范专用目录除外）。
- [x] Task：索引文件让模型翻；把「通用」类重新归类；按动作打标签后过滤；按场景分目录。结果：不行。离线预检高估，真 Agent 经常不翻目录，标签硬过滤丢掉原来能命中的结果。
- [x] Task：规范分级目录、三层目录（通用、仓库、业务）、截取最常用的一批必读。结果：不行。业务层比直接搜索差，截取后基本失效。
- [x] Task：「做事类别、领域，点开分组直接给原文」的规范目录。结果：行，唯一越过门槛的读侧方案，但对照不是严格同时段，真 Agent 的「完全遵守」差异不大。
- [x] Task：分发到个人目录让 Agent 都能用上。结果：放弃。重测发现规模被高估，用户也不支持。

#### Issue：查询改写与排序（无 issue，已完成）

- 结论：不行。
- [x] Task：服务端改写 query、查询规划、意图搜、改调用参数、按仓库加权。结果：不行或收益很小，且更慢。候选放宽有用，但模型筛选又把它们丢掉。
- [x] Task：只搜规范类页。结果：不行，一组任务反而变差。

#### Issue：结果形态与读到不遵守（[#22](https://github.com/yaodiff/memory-lab/issues/22)）

- 假设：读到不遵守的最大类是原文没进上下文。结论：说不清。

- [ ] Task：#22 合成运行里比较摘要与全文，报告已找到的情况下的遵守率。

- [ ] Task：#24 在合成样本上测门槛的准确率与召回率。
